# ADR-0001: 选择 Godot 4 作为 JabJam 游戏引擎

- **状态：已接受（Accepted）**
- **日期：2026-10-10**
- **范围：游戏客户端的引擎选型**
- **依据：** [游戏设计愿景](../game-design-vision.md)

## 决策

JabJam 的游戏客户端采用 **Godot 4.x** 系列。

以 Android 上运行的横屏游戏为首要目标；游戏中结合 **3D 卡通教练、2D 节奏轨道、歌曲播放、运动事件判定与训练 UI**。电视采用手机的普通镜像投屏方式，不作为独立游戏客户端。

**本决策只锁定游戏引擎，不代表整个技术栈已经定稿。** Godot 精确版本、GDScript/C# 的具体分工、渲染器、音乐分析实现、原生 Android 桥接、硬件协议及发布渠道均尚未定案。

## 选择理由

1. Godot 对 2D UI 与 3D 场景/动画混合的游戏组织方式较友好，适合以节奏轨道为操作中心、3D 教练为陪练角色的产品。
2. 引擎开源，便于围绕游戏代码、UI、角色资源及设备适配建立开源社区。
3. 可面向 Android 和未来可能的桌面版本探索，不必从 Web 页面框架开始手工组装完整游戏循环。
4. 以场景/资源为中心的工作流有利于不断替换教练、动作和 UI，符合长期社区共建目标。

## 对比过的方向

- **Unity + C#**：3D 动画与资源生态成熟，但引擎本身不是开源项目，对本项目的开放愿景不如 Godot 契合。
- **Angular + Three.js + Capacitor**：前端语言和业务 UI 开发熟悉，但需要额外承担 3D 动画、音游运行时及 Android 硬件桥接的整合复杂度。
- **Web/PWA 优先**：部署方便，但对 Android 运动手柄底层输入、震动反馈等功能存在更大的验证成本。

上述理由是当下的选型判断，不保证 Godot 在每个技术细节上优于其他引擎。

## 限制和风险

- **Joy-Con 不是引擎内建承诺**：Android 蓝牙连接成功，不等于游戏可读取 Joy-Con IMU 或发送震动命令；可能需要原生插件，甚至因系统 HID 限制无法满足。
- **音游时钟与投屏延迟**必须实测；视觉、音频、运动事件与腕部震动需单独评估同步方式。
- **3D 教练**依赖模型、动画和角色资源制作能力；选定 Godot 不会自动解决素材生产问题。
- **音乐分析**应尽量服务于本地隐私目标，不预设远程服务器或 FastAPI 常驻依赖。
- **禁止摄像头跟踪作为默认方案**：当前产品方向明确不愿使用摄像头。

## 下一步探索（非开发承诺）

- 在目标 Android 手机上验证 Godot 横屏、3D 角色、2D 节奏轨道和本地音频的基础体验。
- 分开验证输入链路：先用模拟事件测试判定与反馈，再研究 Joy-Con/DIY IMU 的真实数据与震动可行性。
- 根据实际演示结果，再决定脚本语言、原生插件边界、音频分析与存储方案。

> **决策原则：** 先确保“喜欢的歌 + 可信出拳判定 + 舒服的节奏反馈 + 训练完成仪式感”能够成立，避免在验证前预先搭建大型插件生态或完整技术架构。
