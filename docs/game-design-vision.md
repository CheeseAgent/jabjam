# JabJam — 游戏设计愿景 / Game Design Vision

> **版本：v0.1（访谈整理稿）｜更新：2026-10-10**
>
> **状态：产品体验愿景，不是技术方案、MVP 范围或开发排期。**
> 本文根据多轮玩家访谈记录“想玩什么”和“哪些地方不能妥协”；功能实现、平台框架、硬件选型均待验证。讨论中的猜想不等于已做决定。
>
> 本文为**当前产品方向的主要参考**；过时的 architecture.md、event-model.md、mvp.md 技术探索稿已从当前分支移除，历史仍可从 Git 记录查阅。

## 1. 一句话介绍

**JabJam 是一款面向手机、可镜像投屏到电视的开源音乐拳击健身游戏：像 Fit Boxing 一样跟着卡通 3D 教练运动，但能使用自己喜欢的本地音乐，并通过真实动作输入、节奏挑战和长期训练记录获得乐趣。**

### 核心体验

用户戴上轻便控制器，打开手机，选择当天的训练计划或自己喜欢的歌曲；在节奏轨道和教练口令的引导下出拳、闪避、流汗。训练结束时，挥出**最后一拳**盖上大拳印，看到本次与累计出拳数量、当天运动记录和长期热力图。

目标不是把健身包装成一场必须天天通关的比赛，而是**让认真运动本身足够好玩**：没破纪录，只要完成今天的训练，也值得庆祝。

### 非目标 / 不应误读

- 不是 Nintendo Switch 模拟器，也不复制 Fit Boxing 的代码、角色、美术、录音或其他受保护素材；仅以其交互体验作参照。
- 不要求专业拳击姿势评分，也不承诺真实拳速、冲击力、热量消耗或医疗级体能测量。
- 不要求每次都刷新纪录才能获得正反馈。
- 不把用户上传/导入的版权音乐放进公开仓库或默认上传服务器。
- **除已单独记录的 Godot 引擎决策外，不要从本文直接推断其他既定开发技术栈或首发版本功能全集。**

## 2. 需求确定性

下列“已确认”代表玩家明确的体验偏好，而非技术可行性已证明。

| 状态 | 内容 |
| --- | --- |
| **已确认：核心方向** | Fit Boxing 风格节奏拳击；自己喜欢的本地音乐；手机端；全程横屏；普通手机镜像投屏到电视；3D 卡通教练；节奏轨道是主要视线焦点；不使用摄像头 |
| **已确认：动作与评价偏好** | 至少区分左右手、直拳/勾拳；错误动作不能算正确命中；重视识别准确、公平连击；出拳速度影响高分的期望；音乐不中断 |
| **已确认：体验偏好** | 本地曲目自动生成拳击谱面；谱面反映音乐情绪/段落；同一歌曲同一配置下谱面固定可重玩；先学基本拳法、以后新歌直接玩；教练喊口令；震动 + 音效 + 画面反馈的理想命中感 |
| **已确认：使用与长期动力** | 一键自动安排约 10 分钟训练，仍可自由选曲；也可以进行约 20–30 分钟训练；打卡日历、每周目标与连胜奖励；Full Combo 挑战；最后一拳真实挥拳盖章；单次及累计出拳数；GitHub 风格出拳热力图 |
| **已确认：社区方向** | 代码开放；希望社区可参与全部模块；教练视觉上保持统一的美术语言；原始音乐由用户本地持有；现有 Joy-Con 可以优先研究兼容 |
| **希望拥有，但细节未定** | 可切换性格和形象的教练、服装/声音/台词、成就/隐藏成就、训练分享卡、类似多邻国的连胜冻结、训练强度选择、左右侧闪和前后步法 |

## 3. 玩家与现实使用环境

- 主要使用：在家中，活动空间约 **2 × 2 米**；手机放桌上，距人约 **1–2 米**；可能镜像投屏到电视。
- 设备原则：**手机负责运行游戏，电视只是手机画面的镜像**；没有确定要做双屏应用或电视原生应用。
- **从首页、选曲、设置、运动日历到正式游玩和结算，全部横屏**。可用 16:9 作为基础构图参考，但需适应不同手机与电视比例。
- 游戏中双手用于拳击；应避免频繁要求触摸手机。暂停、恢复、连接异常等操作方式尚需探索。
- 玩家愿意进行一次性的硬件 DIY/校准，但**日常希望戴上就玩，理想启动约 10 秒**。
- 外设心理预算约 **¥50–100**；愿意增加少量传感器以提升准确性，但不愿频繁佩戴繁琐设备。
- 社区使用门槛：允许按教程购买便宜元件简单组装，不要求首次公开版本做到完全无硬件门槛。

## 4. 核心游玩循环（理想流程）

1. **打开**：横屏主页显示教练、今日训练建议、本周目标/打卡进度和自由选曲入口。
2. **选择**：一键开始由游戏安排的短课（例如 10 分钟，含热身—正式训练—放松），或自由挑本地歌曲；较长课程也可选。
3. **准备**：设备快速连接并确认状态；新用户先学习基本拳法。老玩家不必每首新歌重学。
4. **训练**：玩家主要看**节奏轨道**，3D 教练在画面里示范动作并持续喊口令。左右拳、直拳/勾拳、闪避按节奏判定；失误只影响评价，不打断音乐。
5. **结束**：教练邀请挥出最后一拳，屏幕出现巨大拳印，进入结算。
6. **积累**：展示单次/累计出拳、训练时长、连击与歌曲纪录；更新每天的运动日历、每周目标和出拳热力图；可选生成分享图片。
7. **回来**：下一次可以打喜欢的新歌、重玩熟悉的歌冲 Full Combo，或直接完成今日运动。训练完成本身就是成功。

### 两种入口，不是两种互斥玩法

- **今日训练**：选择时长和强度偏好，自动编排歌曲与动作，减少决策成本。
- **自由选曲**：任意挑本地歌曲，练熟固定谱面，追求最高连击、Full Combo 或单纯享受音乐。

## 5. 音乐与拳击谱面

### 明确偏好

- 支持**用户本地音乐文件**（例如 MP3/FLAC 的需求意向；具体格式兼容性尚待验证）。
- 从节拍、乐句、段落变化和能量起伏生成**有拳击组合感**的谱面，而不是随机在每个鼓点放拳头。
- **音乐高潮更有冲劲、舒缓部分相对放松**；音乐能量是输入之一，而不是训练负荷的唯一依据。
- 兼顾左右手交替、勾拳恢复时间、闪避插入时机、动作连贯性与训练安全性。
- **同一音源 / 难度 / 编排配置下谱面要可复现并能保存**，用于背板、冲击纪录与公平比较；不同难度或重新编排可作为独立谱面，规则待定。
- 一首歌打出 Full Combo 后，依然可以因喜欢这首歌而继续玩；不必强迫不断解锁新内容。

### 待探索的问题

- 能否可靠识别段落情绪，以及情绪与训练强度如何分别定义？
- 强度是谱面生成前估计、生成后评估，还是两者结合？
- 多大程度允许用户编辑或重新生成谱面？如何区分不同版本的纪录？
- 曲目更名、文件更换或不同音频版本应如何匹配历史成绩？
- 音乐播放、判定时钟、蓝牙传感器和电视投屏之间怎样控制可感知延迟？

## 6. 动作识别、评分和打击感

### 想要的动作

- **重点**：左/右直拳、左/右勾拳。
- **希望加入**：左右侧闪（应影响游戏判定/连击）、前后移动和步法（可适当容忍较低精度）。
- 上勾拳、下蹲、格挡等动作在访谈中出现过，但**尚未确认为必须项目**。

### 评价哲学

- 至少区分**左右手与拳法类型**；该左拳时打右拳不能算正确命中。
- 期望在节奏基础上参考出拳速度/动作力度感，软绵绵的出拳不轻易得到最高评价。
- **“速度”“力度感”只是传感器信号的代理指标**，不能直接当作真实力学打击力。
- 允许 MISS，但音乐与训练不停；判定必须让玩家觉得**公平、可信**。设备漏判/误判是重要弃坑风险。
- 无可信传感器时，**不能产生正式的动作成绩或 Full Combo**。是否提供无评分跟练、歌曲预览和测试模拟器，尚未决定。
- 正式评分和动作记录的口径（尝试出拳、成功识别、有效命中、训练累计）需要明确定义。

### 命中反馈：需要实验验证，而非先承诺

理想命中同时有：**音效、视觉效果、腕部短震动**。三者的同步与延迟可能比夸张程度更重要。

可研究不同音效、命中特效、震动强度/时机，但尚不能宣称已经找到“沙袋般”的真实击打感；虚拟震动不能替代物理阻力。

## 7. 教练、视觉与交互

- 整体美术方向：**类似 Fit Boxing 的卡通 3D 教练**；统一、完成度高的商业游戏式视觉语言，但角色和素材应原创或获得可再分发授权。
- **节奏轨道是操作核心**，教练是示范、口令、鼓励与角色陪伴的核心；正式训练时玩家主要看轨道而非持续盯教练。
- 希望角色有可切换的性格、服装和声音；教练连续喊左、右、闪、勾拳等口令。
- 同一首歌玩几十次时，语音重复度、口令音量与音乐平衡值得验证。
- **全程横屏**，布局需考虑电视远距离辨识度，也能在手机上独立玩。
- 节奏轨道可以充分借鉴成熟玩法体验，但应形成 JabJam 自己的标识、素材和视觉表达，不直接复制商业作品的受保护资产。

## 8. 运动养成、仪式感和分享

### 玩家明确喜欢的机制

- 每日打卡日历：当天是否训练、训练数量与强度可回顾。
- 每周训练目标：例如每周完成三次；**连续达标奖励**与每天的运动记录并存。
- 借鉴多邻国的**连胜冻结**想法，但冻结单位、获取方式、恢复机制未定；不能通过断签惩罚强迫受伤或疲劳时训练。
- 训练完成即值得庆祝，即使没有破个人纪录。
- **结束最后一拳盖章**：真实挥拳 → 巨大拳印 → 训练结算。
- 结算显示**本次出拳数、累计出拳数**，辅以时长、连击及歌曲纪录等。
- **GitHub 风格运动热力图**：日期方格，以出拳次数表现活动量（建议单独标记目标达成，避免把“拳多”与“完成训练”混为一谈）。
- 可生成漂亮的分享卡：优先探索长期热力图展示，分享内容/隐私由用户选择。
- 长期奖励：可解锁教练角色外观、口令/互动、勋章、隐藏成就、复杂组合拳与高难课程。

### 设计原则

- 每周目标与休息/恢复共存；无需天天高强度出拳。
- 不以热量、拳数、排行榜等单一数字代表真实健康效果。
- 打卡激励是邀请回来，不应制造不必要的负罪感。

## 9. 硬件兼容设想（尚未选型）

| 方向 | 当前态度 | 需要验证 |
| --- | --- | --- |
| **现有初代 Joy-Con L/R** | 玩家手头有一对，计划日后拿出来测试；**优先探索兼容** | Android 蓝牙双手连接、六轴 IMU 数据可用性、延迟、震动输出、充电/电池状态 |
| **低成本 DIY 运动传感器** | 保留为可复制的开源方案；目标预算约 ¥50–100 | 精度、通信、振动、电池续航、佩戴舒适度与实际物料成本 |
| **辅助躯干/脚部传感器** | 可探索，**未确定需要四个** | 侧闪/步法是否能靠现有设备可靠推断，额外成本是否值得 |
| **手机摄像头** | **明确不希望使用** | 不纳入当前产品体验方案 |

希望不同硬件最终能提供等价的玩法体验，但“开放适配”是产品愿望，**不是已确认的插件协议或技术架构**。

## 10. 开源与社区愿景

- 希望**整个游戏代码**对社区开放，欢迎贡献动作识别、曲谱算法、外设适配、教练、UI 主题、音效、训练课程与记录系统。
- 教练形象应遵循统一美术规范；“所有人都能贡献”不等于“任意画风都直接进入默认角色库”。
- 理想中有清晰的扩展接口，但**尚未决定采用插件、模组、子包或其他组织方式**。
- 本地音乐**不随源代码分发、不默认上传**；未来如果分享谱面，需先处理音乐版本匹配、授权及版权边界。
- 角色、动画、配音、图片、音乐和代码可能分别需要适用的许可协议。**只有原创或权利清楚的素材才可加入仓库**；许可证和投稿规则未定。
- 个人训练数据优先本地掌控；同步、备份、跨设备迁移与分享权限均待设计。

## 11. 主要体验风险与待回答问题

按“可能导致玩家不愿意继续玩”的程度排序，**不是实现排期**：

1. **动作判定可信度**：左右拳/拳法如何避免漏判与误判？官方成绩如何处理设备掉线和低置信度事件？
2. **侧闪/步法识别**：不使用摄像头，能否用 2 个或额外传感器实现足够可信的判定？
3. **音乐—动作—反馈同步**：IMU 采样、无线通信、视觉/音效/震动、电视镜像的延迟如何实测？是否需要分别校准？
4. **动作强度合理性**：如何既表现音乐情绪又避免过密重复动作？正式训练应允许主动暂停和安全退出。
5. **Joy-Con 兼容**：当前只是有设备、尚未实测，不应以蓝牙配对成功推断 IMU 和 HD Rumble 一定可用。
6. **日常启动体验**：常用模式下如何接近“戴上就玩”，连接失败时显示什么、如何恢复？
7. **自动谱面质量**：新歌首轮编排是否真的像拳击训练，固定谱面的版本如何保存与对比？
8. **显示与易读性**：手机小屏、电视远距离的节奏轨道和教练占比；投屏失败时如何继续。
9. **运动记录口径**：出拳数是动作次数、成功识别次数还是谱面命中次数？它们需要避免混淆。
10. **社区素材和持续维护**：如何在开放贡献与统一画风之间建立清晰流程？

## 12. 已达成的方向与暂缓决策

### 不需要再反复争论的方向

- 游戏客户端已选择 **Godot 4.x**，理由与风险见 [ADR-0001](decisions/0001-game-engine-godot.md)；其余技术栈未定。

- Fit Boxing 风格的**教练带练 + 节奏轨道**；
- **自选本地音乐**和按音乐情绪编排、可复玩的谱面；
- **手机运行 + 电视普通镜像投屏 + 全程横屏**；
- **不打开摄像头**，正式计分依赖可信运动设备；
- **运动完成的仪式感与记录**，不把分数当唯一价值；
- **开源、允许社区共同创造**，但艺术风格尽量统一。

### 明确留到以后

- Godot 具体版本、脚本语言分工、渲染器，以及音乐分析 / Android 原生接口 / 本地存储等**其余技术选型**；
- Android 原生应用、PWA、桌面版或 Steam 的平台策略；
- Joy-Con 与 DIY 设备的首发支持范围，以及 IMU / 振动协议；
- 具体算法、打击感实现、评分阈值、UI 效果、角色制作方法；
- 精确 MVP 功能清单、Issue 优先级、里程碑、发布日期和成本承诺。

> **核心判断标准：** 当一个人回到家，打开喜欢的歌，跟着教练打拳、流汗，最后挥拳盖章时，会不会真心觉得“今天运动得好爽，下次还想玩”？如果做不到，额外的 Boss、皮肤和社区系统都不能替代这件事。
